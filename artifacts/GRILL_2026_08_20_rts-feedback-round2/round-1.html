Feedback round 2 — where it lands, how deep it cuts

Seven feedback items land on a codebase where rally points, selection rings, node cards and builder evacuation already exist. This round settles what is actually new, how the build grid is re-cut, and whether the work joins the combat plan or forks its own. Tick answers, add precision, hit copy, paste back.

Plan shape→ Build grid→ Order feedback→ Rally / follow→ Builder trap→ Sandbox scene→ Ticket cut→ Re-baseline budget

Facts read from the tree before asking (not questions — answers)

  • Rally already ships. CommandId::SetRally, Prop::RallyFlag, production.rally[slot], produced units get order_move(rally) (world.rs:2043), HUD prints RALLY x,y. Missing from item 6: rally onto an entity, and any follow behaviour.
  • Selection rings already ship for every selected entity including neutral nodes (pack.rs:400-430, green SELECTION_TINT), and left-click already selects units, buildings and nodes (Pick::Node, world.rs:1052). Node card prints REMAINING n. Item 3 is largely done — the open part is which extra stats to show.
  • Builder evacuation already ships. finish_site (world.rs:1910) plans a destination for every body the footprint covers, and if one evacuee has nowhere to go the site holds at build_ticks - 1 and stays walkable. Item 4's bug is therefore a failure mode of that planner, not a missing feature — likely a permanently stalled site or a body sealed after the stamp.
  • Footprints today: HQ_FOOTPRINT_CELLS = 12, DEPOT = 8, BARRACKS = 10; map 320×320 cells, cell_size_px = 4, unit body radius 3.0 cells (6-cell diameter). Ghost centres on the cursor cell, snaps to nothing.
  • A cell-lattice grid overlay already exists (pack_grid, FramePackOptions::show_grid, a settings toggle) — it draws one line per cell, not per build square.
  • Worker card shows only CARRYING …. Soldier card is hard-coded IDLE. No status taxonomy, no order-target marker, no move marker, no path line anywhere.
  • The scenario is hash-pinned: rts_prototype_v1.sha256 verified at load; tests/rts_acceptance.rs pins exact exit-line counts for both tracked scripts. Any footprint or scene change forces the same re-baseline the combat plan (T7) already budgets once.
  • Combat is planned, not built: no combat.rs, no HP/damage/enemy anywhere in history. Item 7's scenario needs combat plan T1–T3 to exist first.
1. Where does this feedback land relative to the combat plan?

Nothing of phase 2 is implemented yet, so tickets can still be renumbered freely — but item 7 needs combat, and item 1 forces the same scene re-baseline combat T7 already budgets.

2. How big is one visible build square, and how are the three footprints re-cut?

Item 1 fixes two ratios — smallest building = 1 square, barracks = 2×2 — but not the absolute size; today's footprints are 12 / 8 / 10 cells and a unit body is 6 cells across, so a square below 6 cells makes buildings smaller than the units walking past them.

3. When is the visible build grid drawn?

A cell-lattice overlay already exists behind a settings toggle; the build grid is a coarser lattice and needs its own visibility rule.

4. What exactly snaps to the build grid?

Snapping the ghost changes what "valid placement" means and whether the seeded HQ and any future scenario building must sit on a square boundary.

5. Which orders show a target ring, and for how long?

Item 2 wants a persistent green circle on whatever a selected unit is heading toward, surviving deselect/reselect — that means reading it from the order, not from a click event.

6. What is the exact worker status taxonomy on the selection card?

Feedback names six worker states; the card today prints only CARRYING … and a hard-coded IDLE for soldiers. Exact strings become test assertions, so they get pinned here.

7. Item 3 is mostly shipped — what stats are actually missing from the card?

Clicking a building, node or unit already selects it, rings it green and shows a card; the open question is what the card should add.

8. How is the trapped-builder bug fixed, given evacuation already exists?

finish_site already ejects every body the footprint covers, and refuses to finish the building at all if one body has nowhere to go — so your barracks either never finished, or the worker was stamped in by a later change. The fix depends on which.

9. What form do the move marker and path line take?

Item 5 asks for an animation, a flag and a dashed path line; the renderer has texture-free line instances and a props sheet, but no animated-prop path and no per-unit path polyline.

10. How far does the rally upgrade and the new follow behaviour go?

Cell rally already works end to end. The new parts are rally onto an entity, and a Move order that tracks a moving target — a new Order variant that every hash, test and save path must carry.

11. What exactly is in the untimed manual sandbox scenario?

Item 7 is the scenario you asked about earlier: a pre-built base with soldiers and enemies walking in, for hands-on play rather than a timed gate run.

12. How many scene re-baselines are you willing to spend?

Re-cutting footprints changes the pinned scene hash and both tracked scripts' asserted counts — the same one-time cost the combat plan already budgets in its gate ticket. Doing them together is cheaper; doing them apart ships playable feedback sooner.
