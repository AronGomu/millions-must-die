Millions Must Die · Phase 1 · RTS Engine Prototype

An RTS on top of a horde engine, without disturbing the horde

Six systems — camera, selection, workers, economy, building, unit production — cut thin and vertical, on a horde-free scene. The constraint that shaped every decision here: phase 0's contracts stay frozen. The 5 000-agent gate scene's state hash does not move, the render golden is byte-identical, and the scenario contract's atlas_count: 4 still binds every family.

Superseded in part by phase 1.1. This page records the phase-1 slice as it closed. Since then, RTS units gained hard bodies and radius-aware navigation, the camera clamps to a projected frontier with split speeds, the HUD gained a minimap, a command card and a settings menu, and the app gained persistent settings, window modes and generated audio. Nothing below has been rewritten to pretend otherwise — read it beside the phase 1.1 architecture and its functional close.

Two worlds, one binary

The phase-0 Simulation is a fixed-population horde walker: one destination, one flow field, a recycle cursor. Player units need per-unit orders, cargo, construction progress and production queues. Putting those into Simulation would push RTS state inside the type every pinned phase-0 hash digests.

So there are two entity models, side by side, and two commands to drive them. run is unchanged — tests/cli_contract.rs is byte-identical to its phase-0 self, same stdout, same exit-line hash. rts is new, with its own contract suite in tests/rts_cli_contract.rs.

The renderer is the only shared piece, and it was generalised rather than forked: DrawGroup.atlas_id stopped meaning "atlas index" and started meaning "texture slot". With an empty UI layer the emitted bind-and-draw sequence is byte-for-byte what phase 0 emitted, which is why the golden survives.

The RTS tick

Seven systems, fixed order, written into RtsWorld::tick's doc comment so a reordering is a visible diff rather than an accident. Two of the orderings are load-bearing.

  • reads input state
  • mutates entities
  • touches navigation
  • derived, never incremented

Selection self-heal runs after step 7: an entity that died this tick leaves the selection before anything reads it next tick. The whole tick is allocation-free, enforced by crates/mmd-engine/tests/frame_allocations.rs.

Navigation: eight fields, LRU

The engine rule is flow fields, never per-entity pathfinding. A player issues orders to arbitrary destinations, so the answer is a small pool keyed by destination cell. Units sharing a destination share a field — group cohesion for free, and one rebuild instead of N.

Why not per-unit A*. It breaks the stated rule, it needs a per-tick path-request budget nobody has tuned, and it allocates unless a path arena is built first. Three new problems, to solve a problem the existing tech already solves.

Cost of a miss. FlowField::rebuild_in_place reuses the field's own costs/vx/vy buffers plus a caller-owned FieldScratch heap. After warmup a miss allocates nothing; the one documented exception in this phase is that the very first rebuild at a given grid size may grow that heap once.

Invalidation is total. A finished building stamps its footprint blocked and every cached field is invalidated — not the ones that "look affected". One new obstacle can change the descent vector anywhere downstream of it, and a partial invalidation surfaces as units walking into a wall built ten seconds ago.

The worker round trip

One order value, three phases, hashed. The loop's length is dominated by walking, not by mining — which is exactly the macro decision the economy exists to pose.

Two different reach rules, on purpose. A node is one cell, so distance is measured centre-to-centre. An HQ is twelve cells across, so distance is measured to its footprint rectangle — a centre rule would make a worker walk into the middle of its own base to deliver.

Supply is reserved, and usage is derived

Reserved at enqueue. Charging supply when a unit pops would let a player queue five Soldiers into two free supply and get all five. The cap would be decoration. The check order in enqueue_unit is: supply first, then the resource debit — so a supply-blocked enqueue never takes the player's money.

Recomputed, never incremented. Step 7 sums supply_cost over every live unit and adds the queues' reservations. An incremental counter needs adjusting at five call sites — spawn, despawn, enqueue, cancel, store-full recovery — and one missed site is a slow drift the player only notices when production mysteriously stops.

The render layers

A frame is three layers. No third pipeline and no new shader module — the UI rides the same depth-off pipeline the hitbox rings already proved. 

pub struct ScenePass<'a> {
    pub world:   &'a [DrawGroup],       // depth-tested, slots 0..=6
    pub overlay: &'a [SpriteInstance],  // depth off, PROCEDURAL RINGS ONLY
    pub ui:      &'a [DrawGroup],       // depth off, textured, drawn last
}

The rule a contributor can get wrong

overlay binds texture slot 0 and is honest only for procedural ring instances — the shader's ring branch samples no texture, and slot 0 is bound merely because a draw must not leave the pipeline's one declared sampler unbound. A textured instance pushed into overlay will sample the zombie atlas. Textured depth-off content belongs in ui.

As built, that means the overlay layer holds exactly two things: the horde's hitbox rings and the RTS selection rings. Everything else that draws with depth off is a ui group — placement tiles, the drag box, the rally flag, the crystal/gas/supply icons and the HUD panel fill (slot 7), and every glyph (slot 8). selection_rings_are_procedural and hud_uses_only_the_two_ui_groups are the guards.

The camera and the depth key

IsoView::with_center_cell re-derives origin and depth_bias together. That pairing is the whole decision: the depth key is ground_y · depth_scale + depth_bias, and depth_bias carries −origin.y, so the key is a unit's position down the map diamond and does not move when the camera does. Recomputing one without the other makes the crowd re-sort itself as the view scrolls.

deferred Zoom. It multiplies through the tile size, the depth normalisation, the AABB cull and every render golden, and non-integer tile scales shimmer on pixel art. Pan and edge-pan answer the phase's question.

What this phase does not do

  • No combat. The Soldier has no weapon, no health, no behaviour — its selection panel reads IDLE, because anything else would be a claim the code cannot support.
  • No enemy AI, no second faction, no waves.
  • No zoom, no minimap, no fog of war, no save/load, no menus, no sound.
  • No balance pass. Every number above is a placeholder.
  • No real art. Every phase-1 sprite is a generated placeholder, and a real art pass will change every tracked hash — which is the intended failure mode, not a problem.
  • No cross-platform verification. Linux/Vulkan development host only, as in phase 0.
  • No performance number of any kind. Nothing here is measured, published, or gated on. no_perf_claim_in_docs covers this page.

What is actually proven

One tracked script — assets/scenarios/rts_acceptance_v1.script — drives select → gather → build → produce end to end, and it is asserted twice: once through the engine by world state, milestone by milestone, and once through the shipped binary by its exit line. It is in the merge gate.

Alongside it: the horde's run --agents 5000 --frames 300 exit-line hash is unchanged, the host render golden under lab/goldens/ is byte-identical, SpriteInstance is still 48 bytes, shaders/sprite.hlsl is byte-unmodified, and cargo tree -e features | grep -c testkit is still 0.

The frozen phase-0 sim/ took exactly two visibility keywords and one #[cfg(test)] re-export: dir_from_vector became pub so the RTS mover shares the horde's 8-way direction mapping, and step_admissible became pub(crate) so the RTS mover's own copy can be proven equal to it over an exhaustive grid. No signature and no body changed. What phase 1 proves, what it does not, and every known gap: functional close.
