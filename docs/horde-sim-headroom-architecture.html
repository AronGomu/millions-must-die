Horde sim headroom: the separation pass and the isometric render

Two halves. Five changes to one simulation loop, every capability scenario data with an identity default, so a scene that does not opt in walks a bit-identical path — and a render path rebuilt from a flat grid into a 2:1 isometric floor with a depth-ordered draw. The pinned digests are what prove the first half; the second half is downstream of them and moves none.

Why only this loop

The tick has two halves that scale differently. Navigation reads a precomputed flow field — one array lookup per agent, and the field itself is built once. Separation visits neighbours, and the number of neighbour visits tracks the crowd. Age of Empires IV published the shape of that split: raising unit count by a factor of 200 raised flow-field cost by a small factor and steering cost by a large one.

So the flow field is deliberately untouched, and sim::collision::accumulate_separation_phase is the whole subject of the first half of this page. The renderer is the second half, and it is a strictly downstream consumer: it reads simulation state and writes none, which is why nothing in it can move a digest.

The green boxes are the two things phase 0.5 refuses to touch: an agent's step is one step of fixed length, and step_admissible runs on every agent on every tick regardless of phase — so an amortised agent still cannot enter a blocked cell or cut a blocked corner.

The three knobs

All three are required fields on every .ron scenario. A file authored before phase 0.5 fails to parse, deliberately: a stale scenario must never run silently untuned.

Identity means bit-identical. At one phase both amortisation rules degenerate to the pre-phase-0.5 walk. At one mass class every mass is 1, every reciprocal is 1.0, and IEEE multiplication by exactly 1.0 is exact. At one thread no pool is created. The two pinned digests in crates/mmd-engine/tests/separation.rs — BODIED_STACK_HASH and BODYLESS_GRID_PRE_SEPARATION_HASH — are the regression guard for the whole plan, and no ticket is allowed to re-measure them.

The neighbour index

SpatialGrid is a counting sort over fixed-size bins. Two things changed and neither is visible from outside.

Bins carry a stamp

rebuild no longer clears starts before counting into it. Bin populations carry a rebuild stamp; a bin whose stamp is stale reads as empty, and the prefix pass reads zero for it. starts is still written for every bin — including empty ones — because the row window below indexes them. The stamp is u32 and wraps by doing one full clear, so a stale bin can never resurrect an old population.

A row is one run

A bin's linear index is bx + by * cols, and buckets are laid out in ascending linear index. The three bins of one row of the 3×3 window are therefore already a single contiguous run in items. The scan fetches three row slices instead of nine bin slices and gets the identical agents in the identical order — which is why this is bit-exact rather than merely equivalent. An agent whose entire window holds one agent, itself, writes zeroes without touching items.

The worker pool

accumulate_separation_phase reads x, y, mass, inv_mass and the grid — all immutable — and writes only sep_x[i] and sep_y[i]. It is already a pure, index-disjoint, read-only-input pass. Participant w of T owns [w·n/T, (w+1)·n/T).

Every output element is written by exactly one participant, from immutable inputs, in the same intra-agent order it would have had serially. No partial sum crosses a range boundary, so no floating-point reassociation is possible and the result cannot depend on thread count. That is asserted by threads_do_not_change_the_walk, not argued.

The allocation invariant got stronger

alloc_guard.rs used to carry a debt in its own module doc: "Introducing a worker thread on the frame path means this guard must be revisited before it can still claim 'zero allocations per frame'."

Workers arm themselves with alloc_guard::arm_worker() around each chunk. The counter is process-wide and only records an allocation when the allocating thread is armed — so an unarmed worker would be invisible, and an armed one is counted. The existing zero-allocation assertions now cover the pool. A thread that never arms is still invisible, which is exactly what foreign_thread_allocations_do_not_leak_into_a_measure_scope pins, and that test is untouched.

The render half: cell space to a depth-ordered draw

The simulation never learns that the world is drawn isometrically. It keeps positions in cell space — a flat grid of f32 coordinates — and every contact test in the pass above is Euclidean in that space. The projection lives entirely in render::instance::IsoView, which is derived once per scene, and in the vertex stage that reads its two depth scalars. One value computes the tile, the fixed camera origin and both scalars, and both packers plus the uniform upload read it, so the CPU mirror and the GPU cannot disagree about where an agent is or how deep it is.

  • simulation state, read-only
  • CPU pack
  • GPU stage
  • invariant

The camera is a fixed offset that centres the destination cell. Scrolling, edge-pan, zoom and selection are Phase 1, named here so a reader does not mistake the fixed view for an oversight.

Depth is a property of where an agent stands

The key is taken from the quad's bottom edge — the ground point the packer anchored it on — not from the interpolated vertex position. Emitting the per-vertex value instead would give one sprite a depth gradient down its own quad and let it slice into the sprites beside it; all four corners of a quad must carry the same key. The key is normalised over the height of the whole map diamond rather than over the view, so it does not change when the camera does.

The attachment is cleared to 0 and tested with GREATER: an agent one cell nearer walks down the screen, gets the larger key, and wins. Under LESS the horde would draw back to front. A key of exactly 0 fails 0 > 0 and is discarded — drawn nowhere, not drawn last — and an agent on the far corner of the diamond normalises to exactly that, so sprite keys are floored at one quantum of the depth attachment. That floor exists three times over (Rust, the canonical HLSL, and the GLSL the shipped SPIR-V is built from) and shader_defines_match_their_rust_mirrors pins all three against each other, because no test can read a depth value back.

The cutout is what lets the horde stay batched

Depth-buffered draw order needs a per-fragment opaque/transparent decision: a blended fragment that also wrote depth would occlude whatever it was supposed to show through. Pixel art is effectively 1-bit alpha, so the fragment stage discards below the cutoff instead of blending. That is what keeps all four atlas groups drawing in one batched pass with no back-to-front sort, and it is the reason the depth buffer can be trusted at all.

The ring shares the pass with a sentinel, not a second shader

A hitbox ring is a SpriteInstance like any other. There is no second shader file: the vertex stage branches on a negative uv_rect.x, which no atlas rect can ever be, and the fragment stage measures its distance from the quad centre in normalised quad units to inscribe an annulus. Only the pipeline object differs, and only in its depth block — test and write both off — because a debug overlay a unit could stand in front of would stop annotating the thing it exists to annotate. Rings therefore emit an exact z = 0: the far end of the diamond, a value that would fail the sprite pipeline's GREATER test everywhere. That is what makes "the ring pass is not depth-tested" a fact the frame can be asked about rather than an assertion in a comment, and it is asserted by rings_are_never_occluded and a_ring_and_a_sprite_share_a_pass.

The ring traces the body the simulation separates on, so its size is not a free parameter. A circle lying on the isometric floor is an ellipse on screen, and the projection above sends a radius-r circle to semi-axes r·tw/√2 and r·th/√2 — an ellipse that is still axis-aligned in screen space, so an axis-aligned quad remains the right primitive and the shader needs no change. The √2 is easy to drop, and was: the ring first shipped at [2r·tw, 2r·th], the circle's bounding box under the shear rather than its image, so two agents at exactly contact distance drew overlapping rings instead of tangent ones — the one question the overlay exists to answer. The guard is now the geometric property rather than the formula: the_rings_of_two_touching_bodies_are_tangent places a pair at exactly 2r cells and asserts the drawn ellipses touch.

Why none of this can move a digest

The render path reads x[i], y[i], dir[i], frame[i] and the body radius, and writes instance buffers. It writes no simulation state, so no projection change, no depth convention and no ring size can reach the state hash. That is the reason the gate digest is unchanged across the whole of this branch — and, since T10, it is pinned by the_gate_scene_walk_is_pinned_to_its_published_digest rather than by a number re-typed into a document.

What was rejected, and why it will come up again

rejected  Min-corner binning, 2×2 window

Ericson's trick works because each pair is enumerated once and contributes to both members. accumulate_separation is a gather: for agent i it must see every neighbour j, and a 2×2 window anchored at i's min-corner bin misses every j one bin lower on either axis. Converting to a symmetric scatter would write sep[j] from agent i's iteration — destroying the index-disjointness the pool depends on, and contradicting the recorded decision that a cap-truncated pair need not cancel. The transferable half shipped as the row run above.

rejected  An O(#agents) grid rebuild

Reaching it means abandoning the prefix-sum layout for a per-bin linked list, which destroys the bucket contiguity the row run exploits, or sorting the touched-bin list every tick. Neither can be settled by measurement, because measurement is retired. The stamped form ships and earns its keep by giving the scan an O(1) bin_count.

rejected  ORCA/RVO2, and a physical force model

ORCA's own authors document the linear program becoming infeasible in dense conditions and producing global deadlock. The measured power-law force is documented as unstable at timesteps longer than this one. The existing linear falloff and an asymmetric mass byte are the cheaper and safer pair.

rejected  A new dependency for threading

rayon was the obvious candidate. Its parallel bridge carries no documented allocation-free guarantee, and the allocation invariant is a merge gate — "probably fine" is not a standard it can be held to. The cost of refusing is one unsafe impl Send over a pointer descriptor, with its safety argument written next to it.

kept  What did not change

  • The neighbour cap stays at 8 — inside the band every shipped crowd system uses.
  • The coincidence tie-break table, the linear falloff and the 3×3 window are untouched.
  • Separation is still steering, not resolution. Overlap is bounded, never forbidden, and no code or doc may claim otherwise.
  • The movement loop stays serial. recycle_one advances a shared cursor, and that ordering is load-bearing for the cross-process determinism proof.
  • The flow field is outside this plan entirely. The renderer and the shaders are not — see the render half above — but they consume simulation state and produce none, so they are outside the digests.

What this page does not claim

Nothing here has been measured on this engine. Performance measurement is retired for phase 0 and no number gates a merge. Every figure quoted in the ADRs behind this page is someone else's published result, cited to attribute a mechanism.

The acceptance criteria for all five changes are behavioural: identity tunings produce bit-identical state hashes, the threaded pass produces the same output at every thread count, nothing on the tick path allocates on any thread, obstacles are still never entered, and the pool shuts down cleanly. Whether any of it is worth switching on is a question for the optimization phase, with instruments this project does not currently run.
